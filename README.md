# Volleyball Training

Хүүхдийн волейболын сургалтын **бүртгэл, бэлтгэл, ирц, төлбөр, эцэг эхийн харилцаа**-г нэг дор
удирдах веб апп. Интерфэйс бүхэлдээ монгол хэл дээр, цагийн бүс `Asia/Ulaanbaatar`, валют ₮.

- **Admin** — сурагч бүртгэх, бүлэг ба бэлтгэлийн хуваарь үүсгэх, ирц бүртгэх, төлбөр бүртгэх,
  зар нийтлэх, эцэг эхтэй хувийн зурвасаар харилцах.
- **Parent** — бүртгэлтэй утасны дугаар + нууц кодоор нэвтэрч, зөвхөн **өөрийн** хүүхдийн
  оролтын үлдэгдэл, төлбөр, ирц, хуваарь, зар, зурвасаа харна.

## 1. Технологи

| Давхарга | Сонголт | Шалтгаан |
| --- | --- | --- |
| Framework | Next.js 15 (App Router) + TypeScript | Server-side эрхийн шалгалт, нэг кодын бааз |
| UI | Tailwind CSS v4 + гараар бичсэн компонент, lucide-react icon | Гадны CDN хамааралгүй, нэг төрлийн icon сан |
| DB | PostgreSQL (**Supabase**) | Транзакц, `SELECT … FOR UPDATE` түгжээ |
| ORM | Drizzle ORM + drizzle-kit | SQL ил тод, migration файл болон түгжээг шууд удирдана |
| Validation | Zod (сервер тал дээр заавал) | Client-ийн илгээсэн утганд итгэхгүй |
| Auth | Өөрийн session (санамсаргүй token, DB-д HMAC-SHA256-аар хадгална), bcrypt | Нууц код солиход бүх session-ийг хүчингүй болгоно; DB задарсан ч `SESSION_SECRET`-гүйгээр session хуурамчаар үүсгэх боломжгүй |
| Тест | Vitest (бизнес дүрэм), Playwright (E2E) | Эрх/төлбөрийн дүрмийг бодит PostgreSQL дээр шалгана |

**Яагаад Drizzle:** тестүүд нь [PGlite](https://pglite.dev) (WASM PostgreSQL) дээр ажилладаг тул
өгөгдлийн сангийн сервер, нууц үг шаардахгүйгээр **жинхэнэ PostgreSQL семантикаар** бүх
бизнес дүрмийг шалгаж чадна. Production-д ижил schema, ижил migration нь Supabase дээр ажиллана.

### Үндсэн entity-үүд

`users` · `auth_sessions` · `login_attempts` · `students` · `parent_students` · `training_groups` ·
`group_memberships` · `student_status_history` · `training_sessions` · `session_participants` ·
`attendance` · `attendance_history` · `payments` · `announcements` · `announcement_recipients` ·
`conversations` · `messages` · `audit_logs`

## 2. Локал суулгах, ажиллуулах

Шаардлага: **Node.js 20.9+** (24 дээр турших сайн), npm 10+.

```bash
npm install
cp .env.example .env
```

`.env` дотор дор хаяж дараах хоёрыг бөглөнө:

```bash
DATABASE_URL="postgresql://..."          # 3-р бүлгийг үзнэ үү
SESSION_SECRET="..."                     # доорх командаар үүсгэнэ
```

`SESSION_SECRET` үүсгэх:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

Дараа нь:

```bash
npm run db:migrate     # хүснэгтүүдийг үүсгэнэ
npm run create-admin   # анхны админ (5-р бүлэг)
npm run dev            # http://localhost:3000
```

### Сервер суулгахгүйгээр туршихыг хүсвэл (заавал биш)

`.env` дотор:

```bash
DATABASE_URL="pglite://./.pglite"
```

Энэ нь файлд суурилсан WASM PostgreSQL. Зөвхөн **локал туршилтад**; production-д
хэрэглэхгүй. Энэ горимд `npm run db:seed` командаар demo өгөгдөл үүсгэж болно (доороос үз).
PGlite-ийг нэг процесс эзэмшдэг тул **seed ажиллуулсны дараа dev серверийг дахин эхлүүлнэ**.

### Development demo өгөгдөл (зөвхөн локал)

```bash
npm run db:seed
```

1 админ, 2 бүлэг, 10 зохиомол сурагч (төлсөн / төлөөгүй / эрх дуусах дөхсөн / эрх дууссан
жишээ), хоёр хүүхэдтэй нэг эцэг эх, өмнөх ба энэ сарын бэлтгэл, ирц, төлбөр, зар, зурвас
үүсгэнэ. Дахин ажиллуулахад давхар өгөгдөл үүсгэхгүй (админы и-мэйлээр шалгана).
`NODE_ENV=production` үед `ALLOW_SEED_IN_PRODUCTION="true"` биш бол **ажиллахаас татгалзана**.

> ⚠️ Demo өгөгдөл, demo account-ыг production дээр хэзээ ч бүү ажиллуул. Production систем
> хоосон нээгдэж, өөрийн үүсгэсэн админ бодит сурагчаа бүртгэнэ.
>
> `db:seed` ба `db:reset` нь холболтын хаягийг шалгаж, **алсын (Supabase г.м.) сан руу
> чиглэсэн бол ажиллахаас татгалзана** — `NODE_ENV` ямар ч байсан. Санаатай тохиолдолд л
> `-- --yes --allow-remote` гэж дамжуулна.

Бүрэн цэвэрлэх (зөвхөн локал):

```bash
npm run db:reset -- --yes && npm run db:migrate
```

## 3. Supabase холболтын утгыг хаанаас авах

1. [supabase.com](https://supabase.com) → төслөө нээ.
2. Дээд талын **Connect** товч → **Connection string**.
3. Хоёр холболтын мөрийг хуулж авна:

| Зориулалт | Supabase таб | Порт | `.env` хувьсагч |
| --- | --- | --- | --- |
| Апп ажиллуулах (serverless) | **Transaction pooler** | `6543` | `DATABASE_URL` |
| Migration ажиллуулах (DDL) | **Session pooler** | `5432` | `DIRECT_DATABASE_URL` |

4. Мөрөнд байгаа `[YOUR-PASSWORD]` хэсгийг **Database password**-оор солино. Хамгийн хялбар нь:

   ```bash
   npm run db:set-password   # нууц үгийг нууцлан асууж, URL-encode хийж бичнэ
   npm run db:check          # холболтыг шалгана
   ```

   Нууц үгийг олох газар:
   **Project Settings → Database → Database password**. Мартсан бол мөн тэндээс
   *Reset database password* хийж шинээр авна.
   - Гараар бичих бол `@ : / ? # & % + / зай` зэрэг тэмдэгтийг URL-encode хийнэ (`@` → `%40`, `#` → `%23`, зай → `%20`). `db:set-password` үүнийг өөрөө хийнэ.

Жишээ `.env`:

```bash
DATABASE_URL="postgresql://postgres.abcdefghijklm:НУУЦҮГ@aws-0-ap-northeast-1.pooler.supabase.com:6543/postgres"
DIRECT_DATABASE_URL="postgresql://postgres.abcdefghijklm:НУУЦҮГ@aws-0-ap-northeast-1.pooler.supabase.com:5432/postgres"
SESSION_SECRET="..."
```

**Тайлбар**

- SSL нь Supabase host-ыг таниад автоматаар асна (`DATABASE_SSL="disable"` гэж дарж болно).
- Транзакцын pooler (6543) нь serverless-д зориулагдсан — Vercel дээр үүнийг ашиглана.
- Апп нь Supabase **Data API (PostgREST) ашиглахгүй**; зөвхөн серверийн PostgreSQL холболтоор
  ажиллана. Тиймээс `SUPABASE_URL` / `ANON_KEY` шаардлагагүй, browser-т ямар ч DB түлхүүр очихгүй.
- Supabase Auth ашиглаагүй — session-ийг энэ апп өөрөө удирдана.
- `public` schema-г зөвхөн сервер уншдаг тул RLS-д найдалгүй, эрхийн шалгалтыг апп-ын
  давхаргад бүрэн хийсэн. Supabase дээр Data API-г хааж болно (Project Settings → API).

## 4. Database migration

Migration файлууд `drizzle/` дотор SQL хэлбэрээр хадгалагдана (`0000_init.sql`,
`0001_constraints.sql`).

```bash
npm run db:migrate      # DIRECT_DATABASE_URL (байхгүй бол DATABASE_URL) дээр ажиллана
```

Schema өөрчилсний дараа шинэ migration үүсгэх:

```bash
npm run db:generate     # drizzle/ дотор шинэ .sql үүснэ
npm run db:migrate
```

`0001_constraints.sql` нь бизнес дүрмийг **DB түвшинд** бэхжүүлнэ: төлөвийн жагсаалт,
`end_time > start_time`, `amount > 0`, `credits_granted > 0`, зөвхөн `present` бүртгэл
эрх ашиглах боломжтой гэх мэт.

## 5. Анхны админыг аюулгүй үүсгэх

Нийтэд нээлттэй админ бүртгэл **байхгүй**. Админыг зөвхөн серверийн командаар үүсгэнэ:

```bash
npm run create-admin -- --email=admin@tanaisurgalt.mn --name="Батбаяр"
```

- Нууц үгийг гараас **нууцлан асууж, давтуулж** шалгана (дор хаяж 10 тэмдэгт).
- Бичихийн өмнө аль өгөгдлийн сан руу бичихээ (host нь далдлагдсан хэлбэрээр) харуулна.
- **Интерактив терминал шаардлагатай.** Терминалаасаа шууд ажиллуулна уу.

CI/скриптээс ажиллуулах бол нууц үгийг орчны хувьсагчаар өгнө:

```bash
ADMIN_PASSWORD='...' npm run create-admin -- --email=admin@tanaisurgalt.mn
```

- Нууц үг **log-д бичигдэхгүй**, зөвхөн bcrypt hash хадгалагдана.
- Ижил и-мэйлтэй админ байвал нууц үгийг нь шинэчилнэ (нууц үг сэргээх арга).
- Vercel дээр байршуулсан бол энэ командыг **локал компьютерээсээ** production
  `DATABASE_URL`-ийг түр `.env`-д тавиад ажиллуулна (эсвэл Supabase SQL editor-оор биш —
  hash шаардлагатай тул заавал энэ командыг ашиглана).

## 6. Тест ажиллуулах

### Бизнес дүрмийн тест (Vitest, өгөгдлийн сангийн сервер шаардахгүй)

```bash
npm test
```

In-memory PostgreSQL (PGlite) дээр migration-ыг ажиллуулж, эрхийн тооцоо, төлбөрийн
дүрэм, ирцийн зөрчил, харилцааны эрх зэргийг шалгана. **Production өгөгдөлд хүрэхгүй.**

### E2E тест (Playwright)

```bash
npx playwright install chromium   # эхний удаа
npm run e2e
```

`npm run e2e` нь `npm run dev`-ийг өөрөө асаана (`E2E_BASE_URL` өгвөл түүнийг ашиглана).

> ⚠️ E2E тестүүд өгөгдөл **үүсгэж, өөрчилдөг**. Зөвхөн demo seed-тэй хөгжүүлэлтийн
> өгөгдлийн сангийн эсрэг ажиллуул. Production DB рүү хэзээ ч бүү чиглүүл.

### Ажиллаж буй серверийн smoke шалгалт (өгөгдөл өөрчлөхгүй)

```bash
npx tsx scripts/smoke.ts --base=https://tanai-domain.mn \
  --admin-email=... --admin-password=... \
  --parent-phone=... --parent-code=...
```

Нэвтрэлт, эрхийн хамгаалалт, ownership шалгалтыг **зөвхөн уншиж** шалгана — production
дээр ажиллуулж болно (аргументыг өгөхгүй бол тухайн шалгалтыг алгасна).

## 7. Vercel дээр байршуулах

1. GitHub repo-гоо Vercel дээр **Import** хий. Framework: *Next.js* (автоматаар танина).
   Build command `npm run build`, output default — өөрчлөх шаардлагагүй.
2. **Settings → Environment Variables** дотор (Production, Preview хоёуланд):

| Хувьсагч | Утга | Тайлбар |
| --- | --- | --- |
| `DATABASE_URL` | Supabase **Transaction pooler** (порт 6543) | Заавал |
| `DIRECT_DATABASE_URL` | Supabase **Session pooler** (порт 5432) | Migration-д |
| `SESSION_SECRET` | 32+ тэмдэгт санамсаргүй утга | Заавал |
| `DATABASE_POOL_MAX` | `5` | Заавал биш |

   `NODE_ENV`-ийг Vercel өөрөө `production` болгоно — гараар нэмэх шаардлагагүй.
   `ALLOW_SEED_IN_PRODUCTION`-ийг **бүү нэм**.

3. **Бүс (region).** `vercel.json` дотор `"regions": ["syd1"]` гэж заасан — Supabase төсөл
   Sydney (`ap-southeast-2`) бүсэд байгаа тул serverless функцийг мөн тэнд ажиллуулна.
   Хэрэв Supabase төслөө өөр бүсэд шилжүүлбэл энэ утгыг тааруулж өөрчил
   (жишээ нь Singapore → `sin1`, Frankfurt → `fra1`). Буруу бүс сонговол хүсэлт бүр
   далай гаталж, хуудас удаан нээгдэнэ.
4. **Migration-ыг Vercel build дотор ажиллуулахгүй.** Deploy хийхийн өмнө (эсвэл дараа)
   локалаас нэг удаа ажиллуул:

   ```bash
   DIRECT_DATABASE_URL="postgresql://...:5432/postgres" npm run db:migrate
   ```

5. Анхны админаа үүсгэ (5-р бүлэг).
6. Deploy.

**Serverless-ийн тухай тэмдэглэл**

- Холболтын pool нь `globalThis` дээр хадгалагддаг тул нэг lambda instance доторх
  хүсэлтүүд ижил pool ашиглана; холболт эхний query дээр л нээгдэнэ (build үед нээгдэхгүй).
- Бүх хуудас `force-dynamic` — session шалгаж рендэрлэдэг тул кеш хийгдэхгүй.
- Ирц/төлбөрийн эрхэд нөлөөлөх бүх үйлдэл нэг транзакц дотор, сурагчийн мөрийг
  `SELECT … FOR UPDATE`-ээр түгжиж гүйцэтгэдэг тул зэрэгцээ хүсэлтэд давхар эрх хасагдахгүй.

## 8. HTTPS домэйн

1. Vercel → **Settings → Domains** → өөрийн домэйноо нэм.
2. Домэйн үйлчилгээ үзүүлэгч дээрээ заасан `A` / `CNAME` бичлэгийг тохируул.
3. TLS сертификатыг Vercel автоматаар олгоно (Let's Encrypt).
4. HTTPS дээр л session cookie нь `Secure` тугтай явна (`NODE_ENV=production` үед автоматаар).
   HTTP-ээр ажиллуулбал нэвтрэлт ажиллахгүй — заавал HTTPS ашиглана.

## 9. Deploy хийсний дараах шалгалт

Дараах жагсаалтыг **бодит домэйн дээр** нэг удаа гүйцээ:

1. `/admin/login` — админаар нэвтрэх. Буруу нууц үгээр 3 удаа оролдоод хаагдахыг үз.
2. Хяналтын самбар нээгдэж, тоонууд 0 (эсвэл бодит) байх — хуурамч өгөгдөл байхгүй.
3. **Бүлэг үүсгэх** → **Сурагч нэмэх** → түр код гарч ирэхийг шалга (кодоо тэмдэглэ).
4. **Бэлтгэл нэмэх** → жагсаалтад сурагч орсон эсэхийг шалга.
5. **Төлбөр бүртгэх** (12 оролт) → сурагчийн үлдэгдэл 12 болохыг үз.
6. **Ирц бүртгэх** → "Ирсэн" → үлдэгдэл 11 болох; буцаагаад "Тасалсан" → 12 болохыг үз.
7. Өөр browser/утаснаас **эцэг эхээр** нэвтэр (утас + түр код) → кодоо солихыг шаардана.
8. Эцэг эх зөвхөн өөрийн хүүхдээ харж байгааг шалга; URL дээрх `?child=` утгыг өөрчилвөл
   404 гарна.
9. Эцэг эх → админ руу зурвас бичих; админ талд ирсэн эсэхийг шалга.
10. Зар нийтлэх → хүлээн авагчийн тоо зөв, зөвхөн тухайн эцэг эхэд харагдаж байгааг шалга.
11. Гараад дахин нэвтрэхэд бүх мэдээлэл хэвээр байгаа эсэхийг шалга (өөр төхөөрөмжөөс ч).

Эсвэл автоматаар:

```bash
npx tsx scripts/smoke.ts --base=https://tanai-domain.mn --admin-email=... --admin-password=...
```

## 10. Backup ба сэргээлт

**Supabase-ийн суурь backup**

- Free/Pro төлөвлөгөөнд өдөр тутмын автомат backup байдаг:
  **Project Settings → Database → Backups**. Pro дээр *Point-in-Time Recovery* (PITR)
  идэвхжүүлэхийг зөвлөж байна — санамсаргүй устгалыг минутын нарийвчлалтайгаар сэргээнэ.
- Сэргээх: Backups хуудаснаас огноогоо сонгоод *Restore*. Restore нь бүх өгөгдлийг тухайн
  цэг рүү буцаана — өмнө нь одоогийн төлөвөө заавал гараар нөөцөл.

**Гараар нөөцлөх (сар бүр эсвэл том өөрчлөлтийн өмнө)**

```bash
# Бүтэн dump (session pooler холболтоор)
pg_dump "postgresql://postgres.<ref>:<PASSWORD>@<region>.pooler.supabase.com:5432/postgres" \
  --no-owner --no-privileges -Fc -f volleyball-$(date +%Y%m%d).dump

# Сэргээх
pg_restore --no-owner --no-privileges -d "postgresql://..." volleyball-YYYYMMDD.dump
```

**Санал болгох тохиргоо**

- Supabase дээр **Data API-г унтраах** (Project Settings → API): апп нь зөвхөн шууд
  PostgreSQL холболтоор ажилладаг тул PostgREST нээлттэй байх шаардлагагүй.
- Database password-ыг зөвхөн Vercel-ийн environment variables болон локал `.env`-д хадгал.
  `.env` нь `.gitignore`-д бүртгэлтэй — git-д хэзээ ч бүү оруул.
- `SESSION_SECRET`-ийг солих шаардлага гарвал солиод deploy хий; хэрэглэгчид дахин
  нэвтэрнэ (session нь DB-д хадгалагддаг тул шууд хүчингүй болохгүй — шаардлагатай бол
  `auth_sessions` хүснэгтийг цэвэрлэ).
- `auth_sessions` дахь хугацаа дууссан мөрийг үе үе цэвэрлэж болно:
  `delete from auth_sessions where expires_at < now();`

## 10b. Supabase Data API ба өгөгдлийн сангийн эрх

Энэ апп Supabase-ийн **Data API (PostgREST) болон Supabase Auth-ыг ашигладаггүй**.
Сервер нь `postgres://` холболтоор шууд PostgreSQL рүү хандаж, эрхийн бүх шалгалтыг
аппын давхаргад хийдэг: `@supabase/*` сан суулгаагүй, `SUPABASE_URL` / `ANON_KEY`
хэрэглэдэггүй, browser-т ямар ч өгөгдлийн сангийн түлхүүр очдоггүй.

### Хоёр тусдаа давхарга

Эдгээрийг хооронд нь **хольж болохгүй**:

| Давхарга | Юуг шийддэг | Хаанаас удирдана |
| --- | --- | --- |
| **Data API унтраалга** | PostgREST үйлчилгээ ажиллаж, HTTP-ээр нээлттэй эсэх | Supabase Dashboard → Data API |
| **PostgreSQL GRANT/REVOKE** | Холбогдсон дүр юу хийж чадах | `drizzle/0002_lockdown_public_grants.sql` |

Data API-г унтраасан ч `anon`/`authenticated` дүрүүдийн **GRANT өгөгдлийн санд
үлддэг**. Эсрэгээрээ, эрхийг нь хураасны дараа Data API-г дахин асаавал PostgREST
ажиллах боловч тэдгээр дүрд обьектын эрх байхгүй тул хүсэлт `permission denied`
болно. **Data API-г асаах нь хураасан эрхийг өөрөө буцаахгүй** — хандалт сэргэхийн
тулд хэн нэгэн (эсвэл ямар нэг хэрэгсэл) дахин `GRANT` ажиллуулах шаардлагатай.
Supabase платформ ирээдүйд эрхийг автоматаар сэргээх эсэхийг энд **нотлоогүй** —
тиймээс `db:grants --strict` -ийг тогтмол ажиллуулж хянахыг зөвлөж байна.

### Migration-ы хамрах хүрээ

`drizzle/0002_lockdown_public_grants.sql` нь:

- зөвхөн `public` schema, зөвхөн **энэ хэрэглэгчийн эзэмшдэг** обьект;
- зөвхөн `anon`, `authenticated`, `PUBLIC` гэсэн гурван grantee;
- бүх `ALTER DEFAULT PRIVILEGES` нь `IN SCHEMA public` — database-wide мөр үүсгэхгүй;
- Supabase-ийн системийн schema, extension, платформын эзэмшдэг обьектыг хөндөхгүй.

```bash
npm run db:snapshot -- --direct   # одоогийн эрхийг хадгалж, буцаах SQL үүсгэх
npm run db:grants -- --strict     # өмнөх байдал
npm run db:migrate                # 0002-ыг хэрэглэх
npm run db:grants -- --strict     # дараах байдал
```

### Буцаах арга

`npm run db:snapshot` нь `drizzle/rollback/` дотор хоёр файл үүсгэнэ:

- `*_grants_snapshot.json` — бүрэн ACL төлөв (git-д ороогүй, дахин үүсгэгдэнэ);
- `*_grants_restore.sql` — **яг тэр эрхийг** сэргээх SQL.

Буцаах SQL нь `aclexplode()`-оор уншсан бодит эрх бүрийг нэг бүрчлэн `GRANT`
хийдэг — ерөнхий `GRANT ALL` / `ON ALL TABLES` ашигладаггүй, `service_role` -д
хүрдэггүй. `tests/grants-rollback.test.ts` нь migration → буцаалт хийсний дараа
эрхийн төлөв **яг өмнөх хэлбэртээ** эргэж ирж байгааг шалгадаг.

### Энэ migration хаахгүй зүйлс

1. **`service_role`** — PostgreSQL эрх нь бүрэн хэвээр, `rolbypassrls = true`.
   Гурван өөр зүйлийг ялгах хэрэгтэй:
   - *API түлхүүр хүчингүй болгох* (JWT secret солих) → `service_role` -ийн **JWT
     түлхүүр** ажиллахаа болино. PostgreSQL эрхэд нөлөөлөхгүй.
   - *DB эрх хураах* (`REVOKE ... FROM service_role`) → тухайн дүр өгөгдөлд хүрэхээ
     болино. Энэ migration үүнийг **хийхгүй**.
   - *RLS bypass* (`rolbypassrls`) → RLS идэвхжүүлсэн ч `service_role` -ыг
     хязгаарлахгүй. Зөвхөн `ALTER ROLE ... NOBYPASSRLS` арилгана.
2. **`supabase_admin`-ийн default privileges** — `postgres` түүнийг өөрчлөх эрхгүй.
   Платформ `public`-д обьект үүсгэвэл `anon`/`authenticated` тэр обьектод эрх авна.
3. **Ирээдүйн функцийн далд `PUBLIC EXECUTE`** — үүнийг урьдчилан хаах нь
   database-wide өөрчлөлт шаарддаг тул зориуд оруулаагүй. Одоогоор `public`-д функц
   байхгүй. Нэмбэл тухайн функц дээр нь `REVOKE EXECUTE ... FROM PUBLIC` хийнэ;
   `db:grants --strict` илрүүлнэ.
4. **`PUBLIC`-ийн schema `USAGE`** — Supabase-ийн дотоод дүрүүдэд нөлөөлөхөөс
   сэргийлж үлдээсэн. Обьектын эрхгүйгээр өгөгдөлд хандуулахгүй; тиймээс
   `has_schema_privilege('anon', 'public', 'USAGE')` нь `true` хэвээр харагдана.

### RLS-ийн тухай

18 хүснэгтэд RLS **идэвхгүй** тул Dashboard дээр "UNRESTRICTED" гэж харагдана.
Энэ апп Supabase Auth ашигладаггүй тул `auth.uid()`-д тулгуурласан policy бичих нь
утгагүй — **зориуд нэмээгүй**. RLS нь `service_role` -ыг ч зогсоохгүй
(`rolbypassrls`), тиймээс энэ архитектурт жинхэнэ хамгаалалт нь GRANT хураалт.

## 11. Бизнес дүрмүүд

**Оролтын эрх**

- Нийт олгосон эрх = хүчинтэй төлбөрүүдийн `credits_granted`-ийн нийлбэр.
- Ашигласан эрх = эрх зарцуулсан "Ирсэн" ирцийн тоо.
- Үлдсэн = нийт − ашигласан. Сар солигдоход **тэглэгдэхгүй**, шинэ багц үлдэгдэл дээр нэмэгдэнэ.
- Зөвхөн **Ирсэн** нь 1 эрх ашиглана. Тасалсан / Чөлөөтэй / Бүртгээгүй эрх хасахгүй.
- Ирсэн → өөр төлөв: эрх буцаана. Өөр төлөв → Ирсэн: эрх ашиглана. Ирсэн → Ирсэн: өөрчлөлтгүй.
- Үлдэгдэл 0 бол "Ирсэн" болгохыг тайлбартай хориглож, "Төлбөр бүртгэх" товчийг шууд өгнө.
- Сөрөг үлдэгдэл үүсэхгүй; зэрэгцээ хүсэлтэд зөвхөн нэг нь амжилттай болно.

**Төлбөр**

- Нэг бүртгэл = сонгосон сарын бүрэн төлөгдсөн багц. Хэсэгчилсэн төлбөр, өрийн тооцоо байхгүй.
- Сонгосон сард хүчинтэй төлбөр байвал "Төлсөн", үгүй бол "Төлөөгүй".
- Бүртгүүлэхээс өмнөх сар "Хамаарахгүй".
- Нэг сард нэмэлт багц авч болно.
- Давхар submit нэг л төлбөр үүсгэнэ (idempotency key).
- Нийт олгосон эрхийг **ашигласнаас бага** болгох засвар/хүчингүй болголт хоригдоно.
- Түүх устгагдахгүй — `audit_logs` дотор хэн, хэзээ, юуг өөрчилсөн нь үлдэнэ.

**Бэлтгэл ба ирц**

- Бэлтгэл үүсэхэд бүлгийн идэвхтэй сурагчдын жагсаалт (roster) **хөлдөнө**. Сурагч дараа нь
  бүлэг сольсон ч өмнөх roster, ирц өөрчлөгдөхгүй.
- Ирцтэй бэлтгэлийг устгахгүй — цуцлана. Цуцлахад ашигласан эрх нэг транзакц дотор
  буцаж, түүх хадгалагдана.
- Цуцлагдсан бэлтгэлд ирц бүртгэхгүй; болоогүй бэлтгэлд "Ирсэн" тавихгүй.
- Нэг сурагч + нэг бэлтгэл = нэг ирцийн бичлэг (DB unique constraint).

**Эрх ба нууцлал**

- Бүх endpoint дээр серверийн талд role болон ownership шалгана.
- Эцэг эх бусдын хүүхэд, төлбөр, ирц, зурвасыг **татаж ч чадахгүй** (404/403).
- Админы хувийн тайлбар эцэг эхэд хэзээ ч харагдахгүй.
- Нууц кодыг bcrypt-ээр hash хийж хадгална; audit-д нууц үг/код бичигдэхгүй.
- Нэвтрэх оролдлогод rate limit (15 минутад 8 удаа, утас+IP түлхүүрээр).
- Нэвтрэлтийн алдаа нь дугаар бүртгэлтэй эсэхийг задруулахгүй.
- Нууц код солих / reset хийхэд **бүх төхөөрөмжийн session хүчингүй** болно.
- Cookie: HttpOnly, SameSite=Lax, production-д Secure. Мутацийн хүсэлтэд Origin шалгана (CSRF).
- Session token нь 256-бит санамсаргүй утга; өгөгдлийн санд `SESSION_SECRET`-ээр HMAC хийж хадгална.
- Холболт бүтэлгүйтвэл апп PGlite руу **автоматаар шилжихгүй** — алдаа өгч зогсоно.

## 12. Гарын авлага: Admin ба Parent урсгал

### Admin

| Хуудас | Зам | Гол үйлдэл |
| --- | --- | --- |
| Хяналтын самбар | `/admin` | Үзүүлэлт дээр дарж шүүсэн жагсаалт руу орох, өнөөдрийн бэлтгэлд шууд ирц бүртгэх |
| Сурагчид | `/admin/students` | Хайх, шүүх, сурагч нэмэх, дэлгэрэнгүй (Тойм / Ирцийн түүх / Төлбөрийн түүх), төлбөр бүртгэх, түр код олгох, идэвхгүй болгох |
| Бэлтгэл | `/admin/training` | Сарын календарь ба жагсаалт, бэлтгэл нэмэх/засах/цуцлах, бүлэг удирдах (`/admin/training/groups`) |
| Ирц | `/admin/attendance` | Сарын ирцийн хүснэгт (нүд дээр дарж төлөв солих), өнөөдрийн хурдан ирц |
| Төлбөр | `/admin/payments` | Төлбөр бүртгэх, засах, хүчингүй болгох, сараар шүүх |
| Харилцаа | `/admin/communication` | Зар нийтлэх (хүлээн авагчийн тоог урьдчилан харах), эцэг эхтэй хувийн зурвас |
| Бүртгэл | `/admin/account` | Нууц үг солих |

**Шинэ сурагч бүртгэх урсгал**

1. Сурагчид → *Сурагч нэмэх* → нэр, огноо, бүлэг, эцэг эхийн утас.
2. Тухайн утсаар эцэг эх аль хэдийн бүртгэлтэй бол автоматаар холбогдоно (нэг эцэг эх → олон хүүхэд).
3. Шинэ эцэг эх үүсвэл **түр нууц код** нэг удаа харагдана — өөрийн сувгаар (утас, чат)
   дамжуулна. Мартвал дэлгэрэнгүй цонхны *Түр код олгох* товчоор шинэчилнэ.

### Parent

| Хуудас | Зам | Агуулга |
| --- | --- | --- |
| Нүүр | `/parent` | Үлдсэн оролт (том), ашигласан/нийт progress, сарын төлбөр, дараагийн бэлтгэл, сүүлийн ирц, сүүлийн зар |
| Хуваарь | `/parent/schedule` | Ирэх бэлтгэлүүд — огноо, цаг, байршил |
| Харилцаа | `/parent/messages` | Зар (уншсан төлөвтэй) ба админтай хувийн зурвас |
| Профайл | `/parent/profile` | Утасны дугаар, хүүхдүүд, нууц код солих, гарах |
| Ирцийн түүх | `/parent/attendance` | Сараар шүүсэн ирцийн бүрэн түүх |
| Төлбөрийн түүх | `/parent/payments` | Хамрах сар, төлсөн огноо, дүн, олгосон оролт, хүчингүй тэмдэглэгээ |

Олон хүүхэдтэй эцэг эхэд дээд талд **хүүхэд сонгогч** гарч, сонголт бүх хуудсанд дагана.
